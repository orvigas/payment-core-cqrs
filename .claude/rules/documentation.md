# Human-Readable Knowledge Rule (MANDATORY)

The knowledge base is written for software engineers, not for AI models.

## Writing Style

Whenever updating or creating a knowledge document:

- Write in clear, concise, professional English.
- Prefer explanations over raw data.
- Explain the reasoning behind the solution, not only the solution itself.
- Avoid AI-generated sounding language, filler, or repetitive wording.
- Avoid unnecessary buzzwords.
- Write as if another senior engineer will read it six months from now.
- Assume the reader has no context about the original issue.
- Include enough information for someone to understand:
  - what happened
  - why it happened
  - how it was fixed
  - how to avoid it in the future
- Keep entries easy to scan using short sections and bullet points where appropriate.
- Remove duplicated information and update existing entries instead of creating similar ones.
- Prefer examples over lengthy explanations.
- Keep documentation focused on practical knowledge that will save future debugging time.

## Required Questions

Every knowledge entry should answer these questions when applicable:

1. What was the problem?
2. What was the root cause?
3. How was it diagnosed?
4. What was the solution?
5. Why does the solution work?
6. What are the trade-offs or limitations?
7. How can this issue be prevented?
8. Which versions, libraries, or environments are affected?
9. Are there related issues or documentation?
10. What keywords would help someone find this entry later?

## Standard

The documentation should read like an internal engineering wiki, not like AI-generated output.

A developer should be able to understand the issue in less than two minutes and confidently apply the solution without reading the original conversation.
