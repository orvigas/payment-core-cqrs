# Comment Style Rule (MANDATORY)

## Purpose

All source code comments and documentation must read as though they were written by an experienced software engineer maintaining the project.

Comments should help future developers understand the code—not narrate what the code obviously does.

## Scope

This rule applies repo-wide: code comments, Javadoc, README and markdown docs, ADRs, PR descriptions, and commit messages. The plain-text requirement below (no emojis or decorative symbols) also applies to all of these, not just source code.

## Critical Requirements

For every new or modified file:

- Write comments in a natural, professional tone.
- Comments must sound human-written.
- Keep comments concise and purposeful.
- Avoid verbose or overly formal language.
- Avoid repetitive explanations.
- Do not explain obvious code.
- Prefer self-documenting code over excessive comments.
- Update comments whenever the implementation changes.
- Remove outdated or misleading comments.

## Human Writing Style

Comments should:

- Explain **why**, not just **what**.
- Describe intent, assumptions, business rules, or non-obvious behavior.
- Be short and direct.
- Sound like they were written by a teammate during normal development.

Good:

```java
// Retry because the payment provider occasionally returns transient failures.
```

```java
// Keep the original order to match the legacy reporting service.
```

```java
// This cache is intentionally local because the values are request-specific.
```

Bad:

```java
// This method iterates through the list and processes each element.
```

```java
// The following code initializes the object and assigns values to its fields.
```

```java
// This implementation has been designed to efficiently process the collection using modern Java programming practices.
```

## Avoid AI-Like Writing

Do NOT generate comments that:

- Sound like documentation generated by an AI.
- Use unnecessary adjectives.
- Contain generic programming advice.
- Explain every line of code.
- Repeat method or variable names.
- Read like a tutorial.
- Use marketing or promotional language.
- Contain filler text.

Avoid phrases such as:

- "This implementation..."
- "The following code..."
- "It is important to note..."
- "This method is responsible for..."
- "Leverages..."
- "Ensures that..."
- "Robust..."
- "Seamlessly..."
- "Efficiently processes..."
- "Modern best practices..."

## Prefer Self-Documenting Code

Before adding a comment, consider whether:

- A better method name
- A better variable name
- A smaller method
- A better class structure

would eliminate the need for the comment.

Only add comments when they provide information that cannot be easily expressed in code.

## No Decorative Elements

Never use emojis, icons, decorative Unicode symbols, ASCII art, or banner comments — in code, Javadoc, or any project documentation (see Scope above). If existing content contains them, remove them when editing that file unless the user explicitly asks to preserve them.

Not allowed:

```java
// 🚀 Initialize Kafka consumer
```

```java
// ======== Helper Methods ========
```

Preferred:

```java
// Initialize the Kafka consumer before registering listeners.
```

Icons/emojis may only be kept when they are part of user-provided content that must be preserved verbatim, or required by an external spec/protocol.

## Professional Tone

Comments should be:

- Neutral
- Technical
- Clear
- Brief
- Professional

Do not write comments that sound conversational, promotional, or instructional.

## Completion Checklist

Before completing any task, verify:

- Comments sound human-written.
- Comments explain intent rather than obvious implementation.
- No AI-style wording is present.
- No redundant comments remain.
- No emojis or decorative symbols exist.
- All comments accurately reflect the current implementation.

If these requirements are not met, the task is not complete.

This rule is mandatory for all generated or modified source code and documentation.
