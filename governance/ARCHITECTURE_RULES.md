# Architecture Rules

General-purpose architecture and engineering principles for backend services. These rules are stack-agnostic in intent — apply them regardless of language or framework, adapting the specific mechanism (e.g., which concurrency model, which persistence technology) to the project at hand.

## 1. Layering & Dependency Direction

- Separate the system into layers with a single, one-way dependency direction: controllers/API depend on services, services depend on repositories/data access, and nothing lower depends on anything higher.
- Controllers stay thin: request/response mapping, delegation, and status-code selection only. Business logic belongs in the service layer.
- Avoid fat services that absorb responsibilities from every other layer, and avoid anemic domain models where all behavior lives in services and entities are pure data bags. Push behavior onto the domain object when the logic is intrinsic to that object's invariants.
- Keep cross-cutting concerns (security, observability, error handling) in dedicated layers/components rather than scattered inline across business logic.
- When a framework offers two ways to wire a dependency, prefer the explicit one (e.g., constructor injection) over the implicit one (e.g., field injection) — explicit wiring is testable without a container and makes required dependencies visible in the type signature.

## 2. Core Design Principles

- **SOLID**: each component has one reason to change; extend behavior without modifying existing code where reasonably possible; depend on abstractions at layer boundaries, not concrete implementations.
- **DRY**: eliminate duplicated logic, but don't force superficially similar code into a shared abstraction if the two call sites are likely to diverge for unrelated reasons.
- **KISS / YAGNI**: prefer the simplest design that satisfies the current requirement. Don't build for hypothetical future requirements — three similar lines of code are cheaper to maintain than a premature abstraction.
- **Composition over inheritance**: favor injecting collaborators over subclassing to share behavior.
- **High cohesion, low coupling**: a component should have a clearly bounded responsibility and expose the smallest surface area other components need.
- **Immutability by default**: prefer immutable data structures and value objects; make mutability an explicit, deliberate choice, not a default.
- **Fail fast**: surface errors as close to their source as possible, with enough context to diagnose them. Don't swallow exceptions or silently degrade in ways that mask an underlying bug.

## 3. API Design

- URLs are resource-oriented (nouns, not verbs); use HTTP verbs to express the action (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`) instead of encoding it in the path.
- Version the API when a breaking change is unavoidable, and keep the versioning scheme consistent across every endpoint.
- Paginate any endpoint that returns a collection whose size isn't bounded by the domain.
- Make writes idempotent wherever the operation's semantics allow it (safe retries on network failure without duplicating side effects).
- Return structured, machine-parseable error responses with a consistent shape (status, error code/type, message, and enough detail for the caller to act) rather than ad hoc error bodies per endpoint.
- Document every endpoint through the API's schema/spec tooling (OpenAPI or equivalent) as part of implementing it, not as a follow-up task.

## 4. Contracts & Domain Modeling

- Request and response objects should be immutable value types. Immutability at the API boundary prevents accidental mutation between validation and use, and makes the contract easier to reason about.
- Validate at two levels: structural/schema validation (types, required fields, format) as close to the boundary as possible, and business-rule validation (cross-field rules, domain invariants) in a dedicated validation component that runs before the operation executes.
- Translate internal exceptions into API-facing errors at a single, centralized point (e.g., a global exception handler) rather than duplicating error-mapping logic in every controller.
- When an entity's primary key is assigned by application code rather than generated by the database, the persistence layer's default "is this new or existing" heuristic (typically: null ID means new) will misfire. Model new-vs-existing explicitly — track which constructor or code path produced the instance, or use whatever hook the persistence framework provides for this — rather than relying on ID nullness.
- Prefer plain, portable column/field types over vendor-specific ones (e.g., a native enum type) unless you've confirmed your data-access layer's automatic query/SQL generation actually supports that vendor type end to end. A more portable type plus an explicit constraint (check constraint, application-level enum validation) often gives the identical correctness guarantee with far less integration risk.

## 5. Persistence

- Access the database exclusively through a repository abstraction; don't leak query-building or connection-handling details into services.
- Define transactional boundaries at the service layer, around a single logical unit of work. Avoid nesting transactional boundaries inside repository methods.
- Avoid N+1 query patterns — fetch related data in bulk or via a single join/query rather than looping and querying per item.
- Index columns that are filtered or joined on in hot-path queries; validate assumptions with an actual query plan rather than guessing.
- Treat schema changes as an append-only, versioned migration history: every change is a new migration file, migrations are never edited after being applied (edit-after-apply breaks checksum verification and produces divergent schemas across environments), and each migration should be safe to run idempotently in case of partial failure.
- Reach for caching only after simpler options (better queries, pagination, batching, indexing) have been exhausted — caching adds an invalidation problem that pagination and indexing don't.

## 6. Security

- Apply OWASP Top 10 baseline practices as a default, not a checklist reserved for "security-sensitive" endpoints: validate and sanitize all input, encode output, use parameterized queries exclusively, and enforce authentication and authorization on every non-public endpoint.
- Never return passwords, tokens, secrets, stack traces, or internal implementation details in an API response or log line.
- Resolve the authenticated caller's identity through whatever mechanism matches the runtime's concurrency model — thread-bound context works for a one-thread-per-request model, but a non-blocking or coroutine-based runtime needs a context-propagation mechanism that survives execution hopping across threads (e.g., a reactive context, not a thread-local).
- Rate-limit endpoints that are attractive brute-force or abuse targets (login, account creation, anything that triggers an expensive downstream call), scoped per caller/identity rather than globally.
- Hash credentials with a slow, salted hashing algorithm designed for passwords (e.g., bcrypt/scrypt/argon2) — never a fast general-purpose hash.

## 7. Event-Driven Systems

- Publish an event only after the state change it describes has actually been durably persisted — publishing before or racing with the commit lets consumers observe a state that might still be rolled back.
- Don't rely on framework-level "after commit" hooks without confirming they're actually compatible with the transaction manager in use; some hooks are wired to a specific transaction-propagation mechanism and silently stop firing under a different one. If in doubt, publish explicitly at the point the write is confirmed complete.
- Model events as immutable, versioned, typed records — not generic maps or untyped payloads — so consumers get compile-time (or schema-validated) guarantees about shape.
- When a message handler needs to perform multiple related writes, compose them into one atomic unit explicitly (an injected transactional helper, an explicit transaction boundary) rather than assuming the handler's execution model gives you an implicit transaction — some handler contracts (e.g., a callback that must return `void` or a specific SDK type) are incompatible with declarative transaction annotations.
- Design consumers to be idempotent: a message may be redelivered, so processing it twice must not double-apply its effect.

## 8. Resilience

- Wrap every call to an external dependency (another service, a broker, a slow or unreliable resource) with a circuit breaker, so a failing dependency degrades the caller instead of cascading into it.
- Add retries for failures that are plausibly transient (network blips, broker unavailability); use backoff (ideally with jitter/randomization to avoid synchronized retry storms) and a bounded attempt count. Don't retry failures that are permanent (validation errors, 4xx-class responses) — fail fast instead.
- Set an explicit timeout on every call that crosses a process or network boundary, including database calls. An operation with no timeout can hold a resource (thread, connection) indefinitely.
- Tune circuit breaker/retry/timeout thresholds per dependency based on its actual failure characteristics — a flaky non-critical dependency should be more tolerant than one you can't safely serve requests without.

## 9. Observability

- Emit structured (machine-parseable) logs rather than free-text strings — a downstream log store or dashboard should be able to filter and aggregate on log fields.
- Never log secrets, credentials, tokens, or raw personal data. Log identifiers, not the sensitive values behind them.
- If you attach request-scoped context to a thread-local (or equivalent) for logging enrichment, always clear it in a `finally` block. Pooled/reused threads (worker pools, event-loop threads) will otherwise leak one request's context into a completely unrelated later request's logs.
- Instrument new operations with metrics (counters for outcomes, timers for latency distribution, gauges for point-in-time state) and tracing spans as part of building the feature, not as a follow-up. Untraced, unmeasured code paths are invisible during an incident.
- Keep high-cardinality data (user IDs, request IDs, free-text) out of metric labels/dimensions — put it in log bodies or trace attributes instead, where high cardinality doesn't blow up the metrics backend.

## 10. Concurrency Model Discipline

- Once a service commits to a concurrency model (thread-per-request blocking, or non-blocking/async), keep the entire request path consistent with it. Mixing models (e.g., a blocking call buried inside an otherwise non-blocking chain) silently reintroduces the exact problem the chosen model was meant to solve.
- When a blocking call is unavoidable (a legacy client, a driver with no non-blocking variant), isolate it to a dedicated thread pool sized for that workload — never let it run on a thread the rest of the system depends on for throughput (e.g., an event-loop thread in a non-blocking runtime).
- Reserve any "cheap concurrency" primitive the platform offers (lightweight/virtual threads, coroutines) for genuinely blocking I/O workloads, not CPU-bound work — they solve thread-exhaustion-from-blocking, not raw compute throughput.

## 11. Testing

- Follow a test pyramid: many fast unit tests for pure logic, fewer integration tests for behavior that depends on real infrastructure, and a small number of end-to-end tests for critical flows.
- For components whose correctness depends on real infrastructure behavior (vendor-specific SQL, message broker semantics, native driver behavior), test against a real instance of that infrastructure (a disposable container, an embedded broker) rather than a mock — mocks can pass while masking a real integration failure.
- Treat coverage thresholds as a floor that catches obviously untested code, not a target to write tests toward. A test that only satisfies a coverage percentage without asserting meaningful behavior provides false confidence.
- Test failure paths and edge cases explicitly (invalid input, downstream failures, permission denials) — not just the success path.
